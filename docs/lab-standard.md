# 实验室规范

这份规范说明一间实验室要做成什么样。不管是谁做、用什么工具做，照这份规范做出来的实验室应该和已有的实验室是同一个水准、同一种用法。

审核的人和 AI agent 也按这份规范判断一个提交能不能合并。条目都有编号，提意见时请引用编号。

- 怎么参与、怎么提交：见 [`CONTRIBUTING.md`](../CONTRIBUTING.md)
- 写给 AI agent 的简明版：见 [`AGENTS.md`](../AGENTS.md)
- 审核步骤：见 [`review-checklist.md`](review-checklist.md)
- 颜色、字号、组件、封面线稿：见 [`DESIGN.md`](../DESIGN.md)
- 参考实现：压强实验室 `src/labs/pressure/`（规格卡 [`specs/pressure.md`](specs/pressure.md)）

## 1. 一间实验室是什么

**1.1** 一间实验室对应教材的一个单元（一章，或者一个完整的主题）。它由三部分组成：

| 部分 | 数量 | 要求 |
|---|---|---|
| 基础课 | 5 到 8 课 | 严格对应教材这一单元的知识点和实验，顺序和教材一致 |
| 拓展课 | 2 到 4 个小实验，共用一页 | 课本之外的真实情境，界面上标“拓展”，随堂检测不考 |
| 随堂检测 | 9 道选择题 | 每课至少一道易错题，另有综合题；答错可以回到对应那一课 |

**1.2** 每一课让学生**亲手做一件事、读到一个数、得出一句结论**。只看不做的演示动画不算一课。

**1.3** 每间实验室有一张规格卡 `docs/specs/<名字>.md`，先写规格卡、审过了再写代码。规格卡和做出来的东西必须一致；做的过程中改了主意，同一个提交里把规格卡一起改掉，并在卡的末尾“和规格卡原文的出入”里记一笔。

## 2. 制作流程

**2.1** 分四步走，每一步是一个单独的提交请求（PR），上一步合并了再做下一步。

| 步骤 | 交什么 | 审什么 |
|---|---|---|
| ① 认领 | 在总规划表（[`roadmap.md`](roadmap.md)）里那一间的议题下回复 `/认领`；表里没有的，先提一个“新实验室选题”议题 | 是否和已有的重复 |
| ② 规格卡 | `docs/specs/<名字>.md` | 课次编排、每课的动作和数据、大场景的布局 |
| ③ 样板课 | 骨架 + 最能代表这间实验室的一课 | 质感和操作方式是否达标 |
| ④ 其余课 | 剩下的基础课、拓展课、随堂检测；补全首页卡片（封面线稿、课数、入口） | 逐课验收 |

**2.2** 学科老师不写代码也可以参与：只做第 ① ② 步，或者审别人的规格卡、核对数据和用词。

**2.3** 认领不需要等确认，先回复 `/认领` 的人得到这一间，马上可以开始写规格卡。认领之后 14 天内提交规格卡，提交请求的说明里写“关联 #议题编号”；过期没有动静的认领会自动释放。一个人同时最多认领两间。做不下去了回复 `/放弃`。

**2.4** 样板课没有通过之前，不要把其余课一起做完再交。方向错了，返工的是全部。

## 3. 内容

**3.1** 规格卡里写明教材的版本、册、章、节。知识点、实验名称、用词和教材一致。

**3.2** 每课有一句核心概念，不超过 20 个字，是学生做完能说出来的那句话。

**3.3** 每课有 3 到 5 条任务，写成要做的动作（“把探头放到 5 m，记一次”），不写成要懂的道理。

**3.4** 取值约定写在规格卡的总览里，全实验室统一。物理类默认 g 取 9.8 N/kg，水的密度 1.0×10³ kg/m³。

**3.5** 界面上出现的每一个数都要有来历：教材上的数、公认的常数，或者由它们算出来的数。来历记在规格卡里。

**3.6** 拿不准的数据和说法，记到规格卡的“待核实事项”里，**不要写进界面**。宁可少一个数，不要一个可能错的数。不许编造数据、引文、历史细节。

**3.7** 为了看得清而做的简化（把东西画大、把过程放慢、用简化的模型算）可以做，但要在规格卡里写明；如果学生可能当真，界面上要标“示意”或“约”。

**3.8** 不照搬别的产品的代码、画面、文案。可以学习别人的思路。

## 4. 场景

**4.1** **一间实验室一个大场景。** 所有的课放在同一个连续的世界里，各占一处。换课时画面不重建，镜头从一处飞到另一处。

**4.2** 先选一个真实的地方（造船厂、水电站、化肥厂、人体内部），再把实验放进去。器材换成那个地方真有的东西，读数用那个尺度的单位。

**4.3** 规格卡里要有一段“大场景的布局”：各课的器材在场景的什么位置，从哪到哪怎么连起来。

**4.4** 各课的地点和画面要有区别，不能连着几课是同一个机位。

**4.5** 要看水下、地下、物体内部，就把它朝镜头剖开，镜头在剖面这一侧平视。不要从上方透过水面看（看不出物体在水上还是水下）。

**4.6** 场景全部用三维模型，转动视角处处成立。不用照片当背景。

**4.7** 主要器材的模型要有倒角、接缝、螺栓这类细节，不能只是方块和圆柱。

**4.8** 外部素材（贴图、天空图、模型）只用可以自由再分发的许可（CC0 或同等）。每个文件都要登记在 `public/assets/README.md`，写明文件名、来源和许可。能用程序画出来的贴图优先用程序画。

## 5. 操作

**5.1** 界面外壳用 `LabShell`（`@/components/lab/lab-shell`）：顶栏、左上的课程块、右侧的读数面板、底部的操作条。各实验室的位置和样式完全一样，不要自己另做一套。

**5.2** **主操作区最多三个按钮**，而且都是一步到位的（“放到 5 m”“记录数据”）。不放“一步一步微调”的按钮。

**5.3** 微调靠直接操作场景里的东西：拖、点。可以拖或点的东西第一次出现时，旁边要有一句提示，用过一次就消失。

**5.4** 换条件的开关（换液体、换车、换地点）每课最多一组，用分段选择。

**5.5** **永远告诉学生下一步做什么。** 操作条顶上有一行提示语，随状态变化；现在该按的那个按钮轻轻闪。

**5.6** 任务在学生完成动作的那一刻自动打勾，并给出一句结论。全部任务完成时，居中弹出结论卡。

**5.7** 动作要有过程：物体匀速移动，水位慢慢变化，不瞬间跳变。过程进行中，会冲突的操作要禁用。

**5.8** 操作不对时不报错，给一句提示，说明为什么不行、该怎么做。

**5.9** 每课可以“重做本课”。进度存在浏览器本地，键名用 `gewu:<实验室>:<课号>`。

**5.10** 可点区域不小于 44 像素；触摸屏上单指能完成全部操作。

**5.11** **每一课都能自动演示。** 顶栏的“自动演示”按下去，会先重做本课，然后每隔一秒替学生做下一步，一直做到结论卡弹出来。它靠的是 5.5 的“下一步”：现在在闪的按钮会被点一下；在闪的分段选择要用 `want` 写明该选哪一项；下一步不是按钮的（比如要点场景里的东西），这一课用 `LabShell` 的 `autoStep` 自己做。随堂检测的自动演示是按顺序选出正确答案。

**5.12** 键盘：↑↓ 对应主要的升降或增减，空格对应主按钮。在场景里能点、能拖的东西，还要有一个按钮或键盘的等价入口，不能只靠鼠标对准。

## 6. 界面上的字

**6.1** 界面上只出现写给学生和老师看的话。不出现写给开发者看的话（“演示数据”“待确认”“这里只作用于……”）。

**6.2** 原理讲解默认收起，点“看原理”才显示。画面上平时只有一句概念、任务清单、读数和提示语。

**6.3** 这一课的关键参数用参数格单独显示，和公式里的符号一一对应。

**6.4** 数和单位写全，同一个量在全实验室用同一个单位和同样的小数位数。

**6.5** 不加和内容无关的图标、装饰。

**6.6** 画面里的读数标签不小于 16 像素，投屏后排看得清。

## 7. 代码

**7.1** 目录结构固定。用 `npm run new-lab -- <目录名> <中文名>` 生成骨架。

| 路径 | 内容 |
|---|---|
| `labs/<名字>/index.html` | 入口页 |
| `src/labs/<名字>/main.tsx` | 入口：常驻舞台 + 按课号切换 |
| `src/labs/<名字>/lessons.ts` | 课次表 |
| `src/labs/<名字>/physics.ts` | 全部计算 |
| `src/labs/<名字>/physics.test.ts` | 计算的核对 |
| `src/labs/<名字>/world.tsx` | 整个大场景，以及各课的位置表 |
| `src/labs/<名字>/lessonN.tsx` | 第 N 课的界面和任务（拓展课 `lessonx.tsx`，随堂检测 `quiz.tsx`） |
| `src/labs/<名字>/sceneN.tsx` | 第 N 课自己的器材 |
| `docs/specs/<名字>.md` | 规格卡 |

目录名用小写英文、数字、连字符。

**7.2** **计算和画面分开。** 所有的计算写在 `physics.ts` 里，是不依赖界面的纯函数。界面、三维场景、任务判定、随堂检测都从它取数，自己不算。

**7.3** `physics.test.ts` 里每课至少核对一个数，这个数要和规格卡里写的一致。全文件不少于三条。

**7.4** 实验室的代码只能引用三处：自己的目录、公共部件 `@/lab-kit`、界面外壳 `@/components/lab/lab-shell`（以及 `@/lib`、`@/components/ui` 里的通用组件）。**不能引用别的实验室目录里的文件。**

**7.5** 用常驻舞台：最外层放一个 `StageHost`，把整个大场景交给它；每一课用 `LabStage` 交出自己的器材、文字标签和机位。不要每课各建一块画布。

**7.6** 场景里的文字标签用舞台的 `labels`，不要用 drei 的 `Html`。

**7.7** 实验页要能离线运行：不发网络请求，不引用外部地址上的资源。

**7.8** 不随便加依赖。确实需要新的库，在提交说明里写明理由，并单独一个提交。

**7.9** 注释用中文，说明“这是什么、为什么这样做”。每个文件开头有一两行说明这个文件管什么。

**7.10** 类型检查用严格模式，不用 `any` 绕过。

## 8. 自动检查

提交之前在本地跑：

```bash
npm run check
```

它依次做四件事，任何一件不过，提交就不能合并：

| 检查 | 查什么 |
|---|---|
| 类型检查 | 全部代码 |
| 结构检查 `scripts/check-labs.mjs` | 7.1 的文件齐不齐；7.3 测试够不够；7.4 有没有引用别的实验室；7.5 有没有用常驻舞台；7.6、7.7 的禁用项；5.2 主操作区按钮数；5.9 存储键名；5.11 在闪的分段选择有没有写 `want`；6.1 界面里有没有给开发者看的话；4.8 素材有没有登记 |
| 计算测试 | 各实验室的 `physics.test.ts` |
| 打包 | 能不能打出静态文件 |

自动检查查不了的条目（内容对不对、画面好不好、操作顺不顺），由审核的人或 agent 按 [`review-checklist.md`](review-checklist.md) 逐条看。

## 9. 提交时要附的东西

**9.1** 每一课，说明“任务从头做到结论卡”是怎么验证的：人手做的，还是用无界面浏览器自动跑的；哪些操作没有验证到。

**9.2** 每课一张截图（1366×768），另加一张手机竖屏的。

**9.3** 和规格卡不一致的地方，逐条列出来。没有就写“没有”。

**9.4** 没做完、没验证、拿不准的地方，直接写出来。隐瞒问题的提交会被退回。

## 10. 改公共的东西

**10.1** `src/lab-kit/`、`src/components/lab/`、`DESIGN.md`、这份规范、检查脚本，都是公共的。改它们会影响所有实验室。

**10.2** 改公共的东西要单独一个提交请求，不和新实验室混在一起。说明里写清楚：为什么要改、影响哪些实验室、已有的实验室有没有逐个回归过。

**10.3** 新实验室需要的通用能力，优先加进 `lab-kit`，不要在自己的目录里另写一份。

## 12. 这份规范怎么改

规范本身也可以改。提一个议题说明哪一条不合理、打算怎么改；讨论定了，用单独的提交请求改规范，同时改检查脚本和受影响的实验室。
